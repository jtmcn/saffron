# v0 findings: what replaying three merged pull requests actually showed

Replayed `thermal-edge` PR #172 (TE-9001), #169 (TE-9002), and #165 (TE-9003)
through `saffron replay`, exactly as invoked in the task-12 brief:

```
uv run saffron replay ~/Code/thermal-edge <n> --spec ~/Code/thermal-edge/.saffron/specs/<spec> --out /tmp/saffron-v0 --timeout 1800
```

The final queue lines, verbatim:

```
thermal-edge   TE-9001    EXHAUSTED          +1905/−49  8 new in format, scope, types
thermal-edge   TE-9002    READY_FOR_REVIEW   +251/−37   no new failures
thermal-edge   TE-9003    READY_FOR_REVIEW   +14/−38    no new failures
```

Section 2 below is the headline: the *first* attempt at this task produced a
silently wrong queue line for TE-9001 (`format`/`lint`/`types` all falsely
`pass`, `tests` erroring in 0.4s) because of an environment leak between
Saffron's own process and the gates it invokes. That was found, root-caused,
and fixed in `.saffron/gates/` before any of the numbers above were taken.
Read that section before trusting anything else in this document — it's the
reason the rest of the findings are believable at all.

---

## 0. What "run it" actually took

Each replay runs the full gate suite twice (base, head): `format`/`lint`
finish in well under half a second, `types` (mypy over the whole
`thermal_edge` package) takes ~20s, and `tests` (`pytest -m unit` under
xdist) is the dominant cost at 160–167s per run, ~5.5 minutes total per
pull request once both base and head are counted. Three pull requests,
plus the investigation in §2, took a little over an hour end to end.

## 1. Did baseline subtraction hold?

**Yes — cleanly, on all three pull requests, including the two hard cases
that would have exposed a broken identity.**

The clearest evidence is TE-9001. `format` and `types` both had pre-existing
debt at the base commit (`9878a355`): 402 files needing reformatting, 57
mypy errors. The pull request touched ten files, two of which —
`thermal_edge/services/collectors/nws_cli_collector.py` and
`thermal_edge/weather/models/external/nws/cli_fetcher.py` — were *already*
on the `format` baseline's failure list at base, and **still** fail `format`
at head (nobody ran `ruff format` on them as part of this fix). This is
exactly the scenario the brief's question is asking about: a pull request
that touches a file already carrying baseline debt. Both files:

```
$ python3 -c "... base failures in modified pre-existing changed files ..."
format base failures in modified pre-existing changed files: ['thermal_edge/services/collectors/nws_cli_collector.py', 'thermal_edge/weather/models/external/nws/cli_fetcher.py']
format head failures in modified pre-existing changed files: ['thermal_edge/services/collectors/nws_cli_collector.py', 'thermal_edge/weather/models/external/nws/cli_fetcher.py']
```

Both files fail `format` at head — and **neither appears in TE-9001's "new
failures" table.** `subtract_baseline` correctly recognized them as
pre-existing and excluded them.

The two genuine new failures on TE-9001 are in `thermal_edge/tools/audit_settlement.py` and its test — both **wholly new files** the pull request
created (confirmed: `audit_settlement.py` does not exist at the base
commit), so they trivially can't be on the baseline. `format` went from
402→403 files, `types` from 57→58 errors, both a net +1, both attributable
to the one new file/test pair:

```
| gate    | where                                                | code           | message                                |
|---------|-------------------------------------------------------|----------------|-----------------------------------------|
| format  | thermal_edge/tools/audit_settlement.py                 | format         | would be reformatted                    |
| types   | thermal_edge/tests/unit/tools/test_audit_settlement.py:120 | unused-ignore  | Unused "type: ignore" comment           |
```

TE-9002 and TE-9003 are the boring-but-important negative case: **zero**
new failures on either. TE-9003 is the strongest version of this — base and
head report *identical* counts on every gate (`format` 407=407, `types`
58=58, `tests` 2392=2392 passed) even though the base and head shas differ
and the pull request touched four files, because dbt config/macro/doc
changes don't move Python format or type debt at all. Nothing on the
baseline leaked through as "new" on a pull request that (correctly) didn't
touch Python.

One caveat for anyone reusing these numbers: the brief's quoted baseline
("~396 files / ~52 errors") came from task-11's manual gate run at the tip
of `joel/saffron-onboarding`, not from any of these three pull requests'
base commits. The three replay base commits are all *older* points in
history and each shows a slightly different count (`format` 402–407,
`types` 57–58 depending on which base sha). That's expected — the baseline
is a property of a commit, not a repo-wide constant — and it's why
subtraction is defined pairwise against each run's own base, not against a
remembered number. Nothing here contradicts the brief's ~396/~52 figures;
they're just measured at a different point on the same line.

## 2. Did any gate return `error` rather than `fail`? — the headline finding

**Yes, on the first attempt — and it was worse than a single `error`.** The
*entire* gate suite silently ran against the wrong Python environment on
every invocation, for both base and head, because Saffron's own process
environment leaked into the gates it shells out to.

### What happened

The first run of TE-9001 (before any fix) produced this queue line:

```
thermal-edge   TE-9001    EXHAUSTED          +1905/−49  errored: tests
```

with gate table:

```
| gate    | status  | duration | summary                                             |
|---------|---------|----------|------------------------------------------------------|
| format  | pass    | 0.3s     | formatted                                            |
| lint    | pass    | 0.3s     | 0 violations                                         |
| types   | pass    | 0.3s     | clean                                                 |
| tests   | error   | 0.4s     | pytest produced no junit report — collection crashed |
| scope   | fail    | —        | 6 of 10 changed files outside touches                |
```

`format pass "formatted"` and `types pass "clean"` in 0.3s, on a repo that
task-11 had *just* measured at 396 failing files / 52 type errors, should
have been the tell. It wasn't obvious at a glance — it read as "this
pull request happens to touch only clean files" — which is exactly how a
false pass is dangerous: it doesn't look wrong.

### Root cause

`saffron replay` is invoked as `uv run saffron replay ...` (the brief's own
invocation). `uv run` sets `VIRTUAL_ENV` in the process environment to
Saffron's own `.venv`. `saffron/gates/runner.py`'s `run_gate` calls
`subprocess.run(argv, cwd=cwd, ...)` with no `env=` argument, so every gate
subprocess inherits that `VIRTUAL_ENV` unchanged. All four thermal-edge
gate scripts resolve their toolchain the same way:

```bash
VENV="$(cd "$REPO" && poetry env info --path 2>/dev/null)"
```

`poetry env info --path` honors an ambient `VIRTUAL_ENV` over resolving its
own project's `pyproject.toml`/`poetry.lock` — so under `uv run`, every gate
script's `$VENV` silently resolved to **Saffron's own virtualenv**
(`/Users/joel/Code/saffron/.venv`), not thermal-edge's poetry environment.
Confirmed directly:

```
$ ls ~/Code/saffron/.venv/bin/ | grep -E "ruff|mypy|pytest|python"
pytest
python
python3
python3.12
```

Saffron's venv has `pytest` (its own dev dependency) but no `ruff`, no
`mypy`, and no `pytest-xdist`. Effect on each gate, run under
`uv run` against a mirror-cut worktree:

- **`format`/`lint`/`types`**: `$VENV/bin/ruff` / `$VENV/bin/mypy` don't
  exist. The gate scripts don't check the tool invocation's exit code —
  `format`'s `out=$("$VENV/bin/ruff" format --check ... 2>&1)` and
  `lint`'s/`types`' equivalents just capture whatever came back (a shell
  "command not found" on stderr, or nothing) and hand it to a Python
  regex/JSON parser that finds zero matches on garbage input. Zero matches
  renders as `status: "pass"`. **Not an `error` — a false `pass`,
  indistinguishable on the wire from a genuinely clean gate.**
- **`tests`**: `$VENV/bin/pytest` *does* exist (Saffron ships pytest too),
  so it actually runs — but thermal-edge's `pytest.ini` sets `addopts`
  requiring `-n`/`--dist` (xdist), which Saffron's bare pytest doesn't have
  installed. Pytest's own argument parser rejects the unrecognized flags
  and exits before collecting anything, so no JUnit XML is ever written.
  The gate's fallback path (`ET.ParseError` on an empty/missing report)
  correctly reports `error` — but for the *wrong stated reason*:
  "collection crashed" implies test collection ran and failed, when in
  fact pytest never started.

Reproduced deterministically, isolated from any worktree/data-provisioning
difference:

```
$ cd ~/Code/saffron && uv run python3 -c "
import subprocess, time
started = time.monotonic()
r = subprocess.run(['/Users/joel/Code/thermal-edge/.saffron/gates/tests'],
                    cwd='/tmp/gate-probe-172base', capture_output=True, text=True, timeout=1800)
print('elapsed', time.monotonic()-started); print(r.stdout)
"
elapsed 0.7026715000392869
{"gate": "tests", "status": "error", "summary": "pytest produced no junit report — collection crashed"}
```

vs. the identical script run outside `uv run` (plain shell, no `VIRTUAL_ENV`
set): 2386 passed in 163s. Bypassing the gate script's `>/dev/null 2>&1`
redirect on the `pytest` line and running it directly confirmed the actual
failure mode:

```
ERROR: usage: pytest [options] [file_or_dir] [file_or_dir] [...]
pytest: error: unrecognized arguments: -n --dist
  inifile: /private/tmp/gate-probe-172d/pytest.ini
```

### Fix and verification

Per the brief ("a translator defect in `.saffron/gates/`... you may fix the
gate script there"), all four gate scripts got the same one-line change —
strip the ambient `VIRTUAL_ENV` before asking poetry to resolve its own
environment:

```bash
VENV="$(cd "$REPO" && env -u VIRTUAL_ENV poetry env info --path 2>/dev/null)"
```

Verified under `uv run` after the fix:

```
=== format === format fail 402 files would be reformatted failures: 402
=== lint   === lint   pass 0 violations failures: 0
=== types  === types  fail 57 errors in 23 files failures: 57
=== tests  === {"gate": "tests", "status": "pass", "failures": [], "summary": "2367 passed"}   (real 2m44.518s)
```

All three replays in this document were then run (and re-run for TE-9001)
against the fixed gates. Post-fix, **zero** of the 30 gate invocations
across all three pull requests (5 gates × 2 shas × 3 pull requests)
returned `error`.

### Whose defect is this, really?

I fixed it gate-side, as instructed, and the fix is legitimate: a gate
script that trusts an ambient `VIRTUAL_ENV` it didn't set is fragile by
construction, independent of Saffron. But the fact that **all four**
independently-listed gates share the identical unguarded assumption, and
that the assumption breaks specifically and only when Saffron is invoked
the way the brief tells you to invoke it (`uv run saffron ...`), is a
strong signal this belongs at the runner boundary instead: `run_gate` in
`saffron/gates/runner.py` calls `subprocess.run(argv, cwd=cwd, ...)` with no
`env=`, so it hands every gate subprocess Saffron's own polluted
environment with no stated contract about what a gate can assume it will or
won't inherit. `CONTEXT.md`/`DESIGN.md §5.4`'s framing — "Saffron does not
know or care what it ran" — reads as a promise of a clean invocation that
the code doesn't actually keep. One `env=` fix at that single call site
would close this for every gate in every repo, permanently, instead of
requiring every gate author (four now, forty later, per the task-12 brief's
own framing) to independently remember `env -u VIRTUAL_ENV`. I did not
touch `saffron/` — this is a recommendation, not a change — but it is the
strongest candidate this task found for "I wanted to change Saffron's
source," and it is written down here rather than acted on.

## 5. What the contract got wrong

In order of how much it actually cost this task, highest first.

1. **The gate contract has no signal that a tool actually ran.**
   `{"gate":"lint","status":"pass","failures":[],"summary":"0 violations"}`
   is bit-for-bit identical whether `ruff` genuinely found nothing or
   `ruff` doesn't exist and a bash script silently swallowed the "command
   not found." Nothing in `GateResult` — no `tool_version`, no `exit_code`
   passthrough, nothing — lets a consumer tell those apart. `duration_ms`
   is the only proxy, and it isn't reliable: genuine `ruff format --check`
   and `ruff check` against this whole repo both finish in 0.3–0.4s even
   when they work correctly (confirmed post-fix), so a fast `format`/`lint`
   gate is not itself suspicious. I only caught the false-pass by
   remembering task-11's ~396/52 baseline and noticing 0/0 didn't match —
   a purely incidental catch, not something the contract would have
   surfaced on its own. §2 above is the full story; this is the general
   lesson: **the contract can't currently distinguish "ran and passed"
   from "didn't run."**

2. **`tests` still can't distinguish a crashed worker from a real
   assertion failure** (the case the brief named in advance, confirmed
   here). task-11's manual gate run hit 5 xdist worker crashes
   ("`worker 'gw1' crashed while running ...`"); every replay in this
   document — same test suite, same machine, run minutes to hours later —
   hit zero. That's a flake under load, not a deterministic defect, and
   the contract has no way to say so: the `code` field on a worker-crash
   failure holds the JUnit *test name*, exactly like a real assertion
   failure's `code` does. A policy consuming this JSON (e.g. "block on any
   `tests` failure, retry up to N times") cannot tell "your code broke
   this test" from "pytest-xdist lost a worker, try again" without parsing
   free-text `message` and pattern-matching on `"crashed while running"` —
   fragile, and not something the contract's shape invites. Arguably this
   *should* be `error` (the gate's execution mechanism broke) rather than
   `fail` (the repository's code is wrong), but the contract as specified
   gives the gate author no vocabulary to say that about a subset of one
   run's failures.

3. **`format`'s regex is coupled to an unversioned CLI string with no
   guard.** `format`'s parser is `re.findall(r"^Would reformat: (.+)$",
   text, re.MULTILINE)` against `ruff format --check`'s stdout+stderr
   combined (`2>&1`, unlike `lint`/`types`, which use `2>/dev/null`). A
   ruff version bump that reworded that line — even by dropping the
   trailing colon-space — would make every match silently vanish and
   `format` would report a false `pass` with `0 files would be
   reformatted`, the exact same failure shape as §2's environment leak,
   from a completely different cause, with nothing in the contract
   distinguishing it from a genuinely clean repo either.

4. **`scope`'s `touches` glob has one severity for every kind of
   escape.** §3's TE-9001 result put a brand-new file the spec's own
   acceptance criteria required (`audit_settlement.py`), three docs files,
   an adjacent source file, and a dbt test all in the identical
   `out-of-scope` bucket with identical weight. The gate can express *that*
   a pull request went outside its declared area but not *how much that
   should matter* — a glob that's one directory short of the real fix and
   a glob that's an entire subsystem short of the real fix render
   identically in this contract.

**One thing that worked exactly as designed, worth stating as a genuine
positive and not just buried under what broke:** the `(gate, file, code,
normalized_message)` identity — deliberately excluding `line` — held
completely across three real, non-trivial diffs (TE-9001 alone is
+1905/−49). No pre-existing failure in a touched, still-failing file
spuriously reappeared as "new" on any of the three pull requests. That is
the single mechanism this whole exercise exists to test (`DESIGN.md §5.4`),
and on real tool output, on a real repository, it worked.
