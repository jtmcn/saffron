## Findings

- **Blocker: a test outside `touches` asserts the behaviour criterion 4 removes.** tests/test_package.py:2075 reads `assert "parent_branch" not in Path(cli.__file__).read_text()`. Criterion 4 (spec:83) says *"The same path passes the parent's branch to `package()`"*. `package()` only accepts that as the keyword-only `parent_branch` (saffron/phases/package.py:555), so a correct cell fails this test. `tests/test_package.py` is not in `touches` (spec:8–15). **Fix:** add `tests/test_package.py` to `touches`, and name `test_the_operators_reachable_packaging_path_is_unstacked` as the test to invert or delete.

- **Blocker: a child with two unmerged parents is admitted with one parent's work missing.** The gate still requires every `depends_on` to be met (scheduler.py:498–514). Criterion 5 (spec:85) makes `READY_FOR_REVIEW`/`APPROVED`/`MERGE_TRAIN` meet it. Criterion 8 (spec:93) stacks on the first entry only. Built as written, a spec whose two parents are both `READY_FOR_REVIEW` is admitted and cut on parent 1, so parent 2's commits are not in its tree. §4.2.1 (DESIGN.md:379) calls that *"not a smaller version of the feature; it is a version that lies. Without stacking the child branches off `base_sha`, so the parent's changes are not in its tree."* Criterion 8 only asks that it "must not appear to stack on both"; it never asks the gate to refuse. **Fix:** add a criterion that the gate admits a waiting-state parent only for `depends_on[0]`. Any later entry must be `MERGED` or retired, or the child is refused with a reason naming the one-stacking-parent limit.

- **Blocker: the Notes' "gate and resolver agree" argument rests on something false about the code.** Spec:156–157 says *"Every state criterion 3 admits is reached at PACKAGE, which is where `pushed_sha` is recorded — so an admitted parent has one."* At base, `READY_FOR_REVIEW` is written by the cell before PACKAGE runs: session.py:1279 `ledger.set_task_state(task_id, outcome)`, then cli.py:271–282 calls `package`. package.py:561–562 says *"Every `PackageError` this raises is infrastructure and reaches `cli.main`, which exits 2"*. In that case neither `record_push` nor `set_task_package` runs (ledger.py:386–419). The parent stays `READY_FOR_REVIEW` with a NULL `pushed_sha`. Criterion 5 admits it, criterion 9 gives the child an unstacked cell, and that is the same lie as the previous finding. The Notes (spec:160–162) tell the cell to record the disagreement in `BACKLOG.md` "rather than picking one", so the cell is told to ship a hole that is certain to exist. **Fix:** make the gate admit a waiting-state parent only when a row in an admitted state, at the parent's current `spec_sha`, has a resolved `pushed_sha`. Otherwise refuse, with a reason such as "reached `READY_FOR_REVIEW` but never pushed". That needs criterion 1's query to be read by scheduler.py, which is already in `touches`.

- **Blocker: built exactly as criterion 2 says, a merged parent's child is stacked.** Criterion 2 (spec:75–78) says to resolve from the parent's `pushed_sha` and leave it `None` "when the parent has no pushed branch". A `MERGED` row keeps its `pushed_sha`: `reconcile` only calls `set_task_state` (reconcile.py:150), which updates only `state` (ledger.py:311). So a child of a merged parent gets `stacked_on` set to the parent's old pre-merge commit, plus a `parent_branch`. What happens at PACKAGE depends on how the parent was merged:
  - **Squash merge:** the `merge-base --is-ancestor` check fails (package.py:605–613), so `fetch_parent_branch` runs, raises `ParentGone`, and the child ends `MERGE_FAILED`. BACKLOG.md:1810–1816 records this and calls it *"the ordinary shape once a PR lands"*. Whether this repo squash-merges is **unverified**.
  - **Any merge style:** the cell's worktree also misses every commit that landed on the default branch after the parent was pushed.

  The Notes assume the opposite, *"The unstacked fallback in criterion 8 therefore fires only for a merged or retired parent"* (spec:157–159). Criterion 3 (spec:79) leaves the row choice to the cell. A plausible wrong rule, "newest row with a non-null `pushed_sha`", also stacks on `REJECTED`, `CHANGES_REQUESTED` or `MERGE_FAILED` rows. `MERGE_FAILED` rows can carry a sha because `record_push` runs before the PR is opened (ledger.py:386–389). **Fix:** state the rule in the spec.
  - Stack only when the parent is neither in `merged_anywhere` nor retired, and the chosen row is in `READY_FOR_REVIEW`/`APPROVED`/`MERGE_TRAIN` at the parent's current `spec_sha`, matching scheduler.py:585–592.
  - Pick the newest such row.
  - A merged or retired parent gets `stacked_on=None` and `parent_branch=None`.

- **Blocker: nothing stops the obvious wrong implementation of criterion 8.** The spec uses the checklist form, so it declares no witness and no mutant for any criterion (the `acceptance:` witness/`preserves` form exists at intake.py:45–58). A resolver that takes "the first `depends_on` entry that has a `pushed_sha`" never stacks on both parents, so it satisfies *"must not appear to stack on both"* while breaking "only the first entry". **Fix:** add to criterion 8 that when the first entry cannot be resolved and the second can, the cell is unstacked (and, after the second finding's fix, the gate refuses it).
