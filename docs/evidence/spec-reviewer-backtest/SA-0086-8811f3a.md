**Review of SA-0086: re-verify every packaged commit, including when the base did not move**

The fix is sound, but the spec needs two changes before a cell runs it. First, the pull request text it leaves forbidden will say something false on every unmoved-base pull request. Second, criterion 1 can be passed by an implementation that still publishes the cell's own gate table. I read everything at the base snapshot. I ran no test, and one finding (5) is unverified.

## Findings

1. **Blocker: a rendered sentence becomes false, and its file is forbidden.** `saffron/report/pr_body.py:358-361` always renders this for the re-run case: `"Gates were re-run on the **packaged commit**, because the base moved after this task started."`
   - Once `package.py:800` re-verifies on an unmoved base, every unmoved-base pull request, which is most of them, says the base moved when it did not.
   - The spec forbids the file (`saffron/report/**`, spec:21). Its Out of scope (spec:95-97) names only the `_verification("base")` branch becoming unreachable, not the other branch becoming false.
   - A critic lens that flags the sentence raises a blocker the cell is not allowed to fix.
   - **Fix:** remove `saffron/report/pr_body.py` from `forbidden` and put it in `touches`. The wording change is about 4 lines. `tests/test_report.py:646` asserts only `"packaged commit"`, so it survives. The alternative is to list the sentence under item 118's by-hand work (BACKLOG:6684) and land it with this spec.

2. **Blocker: criterion 1 has no mutant, and a wrong implementation passes its witness.** The change edits existing code at `package.py:800`. `docs/agents/issue-tracker.md:89` says: "a spec whose change is an **edit** declares a mutant".
   - The wrong implementation: call `reverify` on every path, but keep `needs_reverification` guarding the `verified_on, gates = "packaged", comparison.run.results` assignment at `package.py:820`. The spec invites exactly that at spec:109 ("Keep that function if you can give it an honest job"). The body then still shows `outcome.gates` and the "base had not moved" sentence on an unmoved base.
   - The witness shape the spec steers toward at spec:120-122, "a test that records whether the fake was called", passes that implementation.
   - The spec's reason for having no mutant is also false: "no text exists yet that a mutant could pin honestly" (spec:101-102). The lines at `package.py:820` and `package.py:828` (`if new := comparison.new_failures:`) exist at base, and the change has no reason to respell them. That is the SA-0064 pattern in `issue-tracker.md:84-87`.
   - **Fix:** declare a mutant on `:820` (replace with `verified_on, gates = "base", outcome.gates`). Or require in the Notes that witness 1 assert the body shows the fake's gate result and not the cell's, the way `test_a_re_verified_body_shows_the_gates_that_re_ran` does at `tests/test_package.py:1761-1792`, but on an unmoved base.

3. **Concern: a wrong criterion 2 note passes both of its tests.** The existing moved-base test checks the note only by substring: `assert "1 new failures after rebase" in result.note` (`tests/test_package.py:1420`).
   - An implementation that appends "the base did not move" to the note unconditionally passes witness 2 and that test. The criterion exists to tell the two cases apart (spec:45-46).
   - **Fix:** in the Notes, require that the moved-base note not say the base did not move. That can be one more assertion in `test_new_failures_after_the_rebase_are_the_tasks_failure`, keeping its name. Optionally add a mutant on `package.py:828`.

4. **Concern: about 22 tests inside `touches` break, and the spec does not warn the cell.**
   - The `packageable` fixture builds an unmoved base, and its docstring says so: "re-verification is provably redundant (no cell, no container, anywhere in these tests)" (`tests/test_package.py:863-865`).
   - Every test that uses it without faking `reverify` will reach `runtime.create_network` and raise `HostToolExecInTest` (`tests/conftest.py:86-91`). That includes the tests at lines 969, 1002, 1053, 1215–1356, 1493–1625, 1795, 2014, 2044, 2064, 2108 and 2188. So do `stacked_packageable` (line 2299) and `test_a_merged_parent_falls_back_to_the_ordinary_target` (line 2347), whose target head also equals `tree_base`.
   - Two tier tests assert the cell's tier reaches the body and the queue line on an unmoved base (`:2023`, `:2036`, `:2051`, `:2061`). After the change, `package.py:825-827` overwrites that tier with the re-run's, so both tests must be rewritten under the same names.
   - The spec (spec:110-113) mentions only tests "that assert an unmoved base skips re-verification".
   - **Fix:** say this in the Notes. Give the three fixtures a default `reverify` fake, and have the two tier tests set the tier on the fake.

5. **Concern, unverified: a test outside `touches` calls a real `package()` on an unmoved base.** `tests/test_session.py:4074` calls `package_mod.package` with `base == tree_base` (`:4039-4041`) and a remote that never moved, and it does not fake `reverify`.
   - Its `_stub_the_runtime` stubs the runtime (`:673-677`), `prepare_worktree` (`:731`), `changed_files` (`:751`) and `run_suite` (`:801-808`). So `reverify` would run `GateSuite` under stubs, and `scope` would probably fail equally at baseline and head and cancel out.
   - I could not confirm that it finishes without an errored gate, drift, or a new failure. If it does not, the cell cannot fix it.
   - **Fix:** run that test against a prototype first, or add `tests/test_session.py` to `touches`.

6. **Concern: a stale claim about DESIGN.md.** The spec says §5.7's "only when the base moved" "is rewritten by hand" (spec:90-93), as future work.
   - At base, `DESIGN.md:1103` already reads "**Re-verification runs on every packaged commit.**", and `:1114` reads "`SA-0086` builds it; until it lands the skip still stands".
   - No criterion depends on it. **Fix:** change the Out of scope entry to say the rewrite has landed.

7. **Note: the spec uses a word CONTEXT.md reserves.** `CONTEXT.md:287` says to avoid "verdict" for a suite comparison, because "that is the critic's confirm-or-withdraw of a finding". The spec uses it in claim 2 (spec:46, "a verdict that did not reproduce") and in the Problem section (spec:82). `DESIGN.md:1135` uses it the same way. The claim is rendered into the pull request body, so it is worth rewording.
