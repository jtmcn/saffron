## Findings

1. **Blocker: criterion 4's witness passes on unfixed code, so the `revert` gate fails it.** Spec line 53: *"Neither a concurrency flag nor a multi-repo flag exists."*
   - **What's wrong:** at `base` there is no `batch` command at all, so the claim is already true there. The subcommands are only `replay`, `cell`, `queue` and `reconcile` (`saffron/cli.py:73-105`). The natural test, `pytest.raises(SystemExit)` on `main(["batch", "--concurrency", "3"])`, passes before and after the change, because argparse rejects the unknown `batch` choice with exit 2 either way.
   - **Evidence:** `revert` runs every declared witness with the source reverted (`saffron/gates/core/revert.py:127-128`, `declared = {c.witness for c in acceptance}`). A pass there becomes `status="fail"` (`revert.py:303-306`). `revert` is always blocking (`ontology/saffron.ttl:83`, `saffron:revert … saffron:blockingAt saffron:alwaysBlocking`), and `cli.py` counts as source because `.saffron/policy.yaml:28` sets `test_paths: ["tests/**"]`. The review brief's own rule: *"a non-`preserves` witness must not already pass at base"* (`DESIGN.md:837`).
   - **Fix:** reword the claim so the witness first proves `batch` accepts `--repo`, `--budget` and `--until`. Only then should it assert that `--concurrency` and `--repos` are rejected by the batch subcommand's own parser, not by an "invalid choice" for `batch`. Criterion 7's "never 1" walk has the same weakness if written as "caught `SystemExit`, code ≠ 1"; give it the same positive half.

2. **Blocker: no criterion requires the adapter to run PACKAGE, and an adapter that skips it passes all 11 witnesses.** The spec declares no mutants.
   - **What's wrong:** the attended path packages a `READY_FOR_REVIEW` outcome and passes `parent_branch=target_branch` (`saffron/cli.py:469-486`). The loop only needs the runner to return a `CellOutcome` (`saffron/batch.py:97`). An adapter returning `run_one_cell(...)` directly satisfies criteria 10 and 11, which are about `CellSpec.stacked_on`. The spec's only mention of shape is spec lines 166-167: *"Read `_run_cell` for the adapter's shape"*.
   - **Why it matters:** a batch built that way pushes no branch and opens no PR. Every child would then hit *"records no pushed branch"* (`cli.py:319-325`) and run unstacked, which is the silent failure the spec warns about in lines 162-164.
   - **Fix:** add a criterion saying a `READY_FOR_REVIEW` outcome is packaged with `parent_branch` equal to the resolved branch, or `None` when unstacked. Model its witness on `tests/test_cli.py:683`, `test_a_stacked_worktree_passes_its_parents_branch_to_package`.

3. **Concern: reusing `_ceilings` with the batch command's arguments silently sets every task's budget to the batch budget.** Spec lines 169-170: *"the ceilings, which a batch takes from the spec because no flag overrode them"*, alongside *"reuse rather than reimplement"*.
   - `_ceilings(args, spec)` reads `args.budget`, `args.max_attempts` and `args.max_turns` (`cli.py:162-166`). The batch's `--budget` defaults to 50 and means the batch budget. Passed through, it becomes each task's `budget_usd` labelled "(flag)". The missing `max_attempts` attribute would raise `AttributeError` on every candidate; the loop catches that as an abort (`batch.py:158-172`), so the breaker ends the night as `INFRASTRUCTURE`.
   - No witness pins the per-task ceilings. **Fix:** tell the adapter to call `_ceilings` with a namespace whose three fields are `None`, and add a witness.

4. **Concern: the adapter cannot resume a candidate's task row, and the spec does not say so.**

5. **Concern: readiness necessarily runs after the scan, so some failures never reach criterion 9's "which step failed".**
