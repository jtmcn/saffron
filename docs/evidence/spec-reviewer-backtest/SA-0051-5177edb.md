## Findings

- **Blocker — nothing the command wires up exists at base.**
  - **What the spec says:** "`SA-0050` built `run_batch` and left it with no caller" (spec:125). It forbids the files that would have to hold it: `saffron/batch.py` (spec:15), `saffron/ledger.py` (spec:22), `saffron/preflight.py` (spec:24). The notes also rely on "`check_readiness` returns a result … `ok`, … `step` and a `detail`" (spec:175–177).
  - **What base has:** `saffron/batch.py` does not exist. `ledger.py:3` says "Seven of the ten tables. `batches` and `decisions` wait for a scheduler", and its only tables are at 17–98, so there's no `batches` table. `create_run(self, repo_id: int, base_sha: str)` (ledger.py:325) takes no batch id. There's no readiness entry point: `preflight.py:1` reads "Per-run readiness: two probes", and none of its functions (37–253) is one.
  - So SA-0045, SA-0048, SA-0049 and SA-0050 have all not landed here. That's odd, because `history` shows SA-0045 and SA-0048 as `MERGED` on 2026-09-04. Which side is stale is **unverified**.
  - **Effect:** criteria 1, 4, 5, 6, 7 and 9–11 (spec:32–104) all call a function, table or result type that isn't there, in files the cell may not edit. Every attempt would fail `scope`, or fail its witnesses at head.
  - **Stacking doesn't save it:** it only consults `depends_on[0]`, and "a grandchild … is out of reach by design" (cli.py:260–263). A cell stacked on SA-0050 would only have SA-0048 and SA-0049 if SA-0050's own branch already carries them.
  - **Fix:** cut the cell from a base where all four specs have merged. Then re-check the readiness name: the plan calls it `batch_preflight(...)` (docs/superpowers/plans/2026-09-04-batch-orchestration.md:177), while this spec says `check_readiness`.

- **Blocker — the adapter criterion doesn't pin how the adapter sets ceilings or runs PACKAGE.**
  - **What the spec says:** the notes call the adapter "what turns a candidate into a cell" and say it needs "this module's own ceilings resolver" (spec:190–193). Criterion 9 (spec:84–93) only checks the stacked branch and sha. At base, `Criterion` has no `mutant` field and uses `extra="forbid"` (intake.py:51–57), so nothing in the spec catches a wrong build.
  - **Wrong build 1, which passes that witness:** reuse `_ceilings(args, spec)` with the batch's own arguments.
    - "The flag wins when it is given" (cli.py:151, 165–167), so `--budget 50` would replace every task's `budget_usd`.
    - `args.max_attempts` doesn't exist on the batch parser. If it raises, every task raises; if it's worked around with `getattr`, the budget override happens without any sign.
  - **Wrong build 2, which also passes:** call `run_one_cell` without `package_phase.package`. In `_run_cell` the caller runs PACKAGE (cli.py:469–486), so a `READY_FOR_REVIEW` task would never get a PR.
  - **Wrong build 3, which also passes:** reload the spec with `load_spec(candidate.path)`. That path lives in a temporary directory deleted when `_queue`'s `with` block ends (cli.py:527–547), so the load raises. The fix is to use `candidate.spec` and `candidate.spec_sha` (scheduler.py:129–132).
  - **Fix:** add criteria, with witnesses, saying:
    - the adapter's ceilings come from the candidate's spec and never from `--budget`;
    - a `READY_FOR_REVIEW` outcome goes through PACKAGE with `parent_branch=target_branch`.

- **Blocker — criterion 8 claims behaviour base already has, but uses a new witness that isn't `preserves`.**
  - The claim says "the existing behaviour, asserted here …" (spec:77–83).
  - At base, `test_an_in_flight_task_survives_being_looked_at` (tests/test_cli.py:1631–1649, parametrised with `["queue", "reconcile"]`) already asserts that `IMPLEMENTING` survives `queue`.
  - A renamed copy gets past `witness-green-at-base` (criteria.py:97–102) only because the node id is new, so it proves nothing.
  - **Fix:** `witness: tests/test_cli.py::test_an_in_flight_task_survives_being_looked_at[queue]`, `preserves: true`.

- **Concern — criterion 11 mixes a regression guard with a structural claim that no behaviour test can tell apart.**
  - "The attended command's printed output is unchanged" (spec:101–103) has the shape of `preserves`. The queue tests at base already pin it (tests/test_cli.py:1208–1225, 1380–1542).
  - "One scan feeds both commands" (spec:100) would pass just as well with a copied scan.
  - **Fix:** split it in two:
    - a `preserves: true` criterion on an existing queue test;
    - a new witness that patches the shared scan helper and asserts both `queue` and `batch` reach it. That helper's use must also differ in the one named argument.

- **Concern — once this lands, docstrings in two forbidden files become false.**

  - `scheduler.py:121–123`: "neither `queue` nor `reconcile` is a batch scan — so a corpse still reaches this function unstamped."

- **Concern — the night can't resume a task row, and §4.2.1 requires it.**

  - So every re-queued `CHANGES_REQUESTED` or stamped `ORPHANED` task gets a new row. That includes the corpse criterion 7 re-queues.
  - **Fix:** name it in Out of scope along with the follow-up spec that will handle it.

- **Concern — printing the readiness step isn't a criterion, and whether `run_batch` can report it is unverified.**
  - The notes require it: "A night that dies at readiness must print the step" (spec:177).
  - SA-0050 has `run_batch` return only the stop reason, and readiness is a keyword with a default (SA-0050 spec:158, 201–204). So the command has to wrap the readiness callable to capture the step.
  - No witness checks it. **Fix:** add one, or drop the requirement.
