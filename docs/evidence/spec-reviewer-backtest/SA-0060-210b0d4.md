## Findings

1. **Blocker.** `SA-0060…md:103-106`, which criterion 3 relies on (`:48-53`, *"it is the reason the restore lives in the exit path rather than in a `finally` the gate writes"*). The spec says that swallowing a Ctrl-C and having an `OSError` from `finally` replace an interrupt are *"Both … shapes a context manager's exit does not have."* The second half is false. An exception raised from `__exit__`, or from a `@contextmanager`'s `finally`, replaces the one in flight, exactly as it would from a bare `finally`.
   - **The precedent the spec copies already has this defect.** `worktree.py:338-342` restores from `finally: _restore_source(...)`, which raises `CellRuntimeError` (`worktree.py:307-311`). `revert.py:204-211` then does `except Exception as exc: return GateResult(... status="error" ...)`. So a Ctrl-C during `revert`'s run, followed by a failed restore, comes out as an ordinary `error` result.
   - **Built to the letter, it breaks base's own guard.** Suppose the host mutator is `try: yield / finally: restore_mutant(...)` and the gate catches exit exceptions to report `error`. Then `test_witness_gate.py:339-359` (`…_does_not_replace_the_interrupt`) breaks.
   - **The new witness can't catch it.** Base says *"A plain interrupt with a clean restore always propagated"* (`test_witness_gate.py:317-320`). So `test_an_interrupt_still_propagates_through_the_new_seam`, driven by a fake context manager that restores cleanly, passes against the broken build.
   - **Fix:**
     - Correct the Problem paragraph.
     - Make criterion 3 say that its witness interrupts *and* makes the restore raise, in both ways base tests: tree moved (`:313-336`) and file deleted (`:339-359`).
     - Say which side stops an exit exception from replacing an in-flight `BaseException`.
     - Declare a mutant, e.g. drop that guard from the host mutator's exit.
