- **Blocker: the base does not contain what the spec builds on.** At `saffron/gates/core/witness.py:59-64` the gate still takes `tree: Path`. `saffron/gates/runner.py:300` still has `tree: Path | None = None`, and `saffron/cell/session.py:966` still calls `run_suite(gates, cwd=repo, executor=executor)` with no mutator and no stub.
  - The spec's Context (`SA-0062…md:71-73`) says: "`SA-0060` gave the gate an injected mutator; `SA-0061` wired a stub into a cell run and turned the gate on. This replaces the stub." Neither change is at base.
  - Both specs sit in `.saffron/specs/`, not in `done/`, and neither has a row in `history`.
  - `saffron/gates/**` is `forbidden` (`:20`), so a cell cut from this base cannot give a Path-typed gate a context-manager mutator. Criterion 5 (`:61`, "supplies this mutator in place of the stub") has no stub to replace.
  - The scheduler would refuse it anyway (`saffron/scheduler.py:587`: "depends_on {dep} has no task at its current spec_sha"), so this is only a risk if someone forces it with `saffron cell`.
  - **Fix:** run this only after `SA-0061` has merged, or is stacked on. Then re-review it against the callable contract `SA-0060` actually lands.

- **Blocker: undoing with `git checkout HEAD` destroys uncommitted edits and hides them from `committed`.**
  - Criterion 2 (`:43-46`) says: "The agent's work is committed by the time gates run — `committed` is what guarantees it … and `revert` restores the same way for the same reason."
  - That is false at base. `committed` guarantees nothing: it checks for a dirty tree and fails (`saffron/gates/core/committed.py:21-25`; DESIGN.md:765, "the worktree is clean at gate time").
  - It also runs *after* the declared suite `witness` sits in: `session.py:966` is `run_suite`, and `session.py:1001` is `committed_gate(...)`. Uncommitted edits are ordinary there; the host only commits them on a turn that ended abnormally (`session.py:1401-1405`, `1522-1526`).
  - `revert` does not restore "the same way for the same reason". It refuses dirty paths first, because of exactly this problem (`saffron/gates/core/revert.py:174-179`): "an uncommitted edit to a source path does not survive this gate — and `committed` runs next and would report the tree clean … no evidence about theater is worth destroying the agent's uncommitted work and blinding the gate that would have caught it."
  - Built as written, `source_mutated` wipes a dirty `mutant.file` and turns a `committed` `fail` into a `pass`.
  - The criterion 2 witness makes this worse. "Restores the committed file, not a byte copy" can only be observed on a file whose worktree content differs from `HEAD`, so the test would enshrine the data loss.
  - **Fix:** have `source_mutated` refuse, via `dirty_paths`, when `mutant.file` is dirty. Report that however `SA-0060` spells "did not apply"; `worktree.py` is in `touches`. Reword criterion 2, and add a witness that an uncommitted edit to the mutated file survives.

- **Blocker: criterion 5's witness cannot tell the real mutator from the stub, and it declares no `mutant`.**
  - At base the gate returns `skip`, "the spec declares no mutants", before it could consult any mutator (`witness.py:77-81`). `run_witness` skips its probe when nothing is declared (`runner.py:234-235`).
  - `SA-0060` forbids changing verdicts (`SA-0060…md:115-117`): "A verdict that changes here is a defect."
  - So on every spec in the repo, the stub and the real mutator produce the same `witness` gate result. The Problem sentence (`:77-78`, "every `witness` result is `skip` for the wrong reason") is false at base.
  - Plausible wrong implementation: wiring `source_mutated` with the wrong first argument (`repo`, `spec.tree_base`), or leaving the stub in place. A witness that asserts the `skip` passes either way.
  - **Fix:** drive a spec that *declares* a mutant through `_stub_the_runtime`, monkeypatch `worktree.source_mutated`, and assert that it receives the cell's container name. `source_reverted` is stubbed the same way at `tests/test_session.py:775-784`. Declare a `mutant` on this criterion as well.

- **Blocker: criterion 3 declares no `mutant`, and a plausible wrong implementation passes its witness.** The spec edits existing code (`session.py`, `worktree.py`), so each criterion needs a mutant. The host rule the spec cites counts byte occurrences (`saffron/mutation.py:130-144`). An in-cell version built on `grep -c` counts *lines*, so it would apply a `find` that matches twice on one line. A witness whose two matches sit on separate lines passes that implementation.
  - **Fix:** declare mutants for criteria 2–4 too. The host's gate will `skip` them for now, but they record what would falsify each claim. Make the criterion 3 witness include a same-line double match.

- **Concern: criterion 4 contradicts criterion 3 and §5.4.1.**
  - Criterion 4 (`:55`): "A failure to apply or to undo raises rather than reporting a verdict, and the gate turns that into `skip` or `error`."
  - DESIGN.md:919-921: "A mutant that does not apply is named … the result *names* every such criterion."
  - `mutation.py:29-32`: "Applying never raises … because a mutant that does not apply is the ordinary case."
  - If "failure to apply" covers a `find` that did not match, and `SA-0060` turns a raise into the whole gate's "cannot reach the tree" `skip`, then one stale mutant discards every other criterion's finding. That is the harm `runner.py:203-209` warns about. **Unverified**, because `SA-0060`'s contract is not at base.
  - **Fix:** say that "raises" means only that the container or git broke, and that a `find` not matching exactly once is reported per criterion.

- **Concern: the spec never says how the in-cell apply works, and the obvious routes break something.**
  - `runtime.exec_` takes no stdin (`saffron/cell/runtime.py:269-281`), and it decodes stdout with `errors="replace"` (`:111-114`). Reading a file through it loses bytes that are not valid UTF-8, and `runtime.py` is not in `touches`.
  - Doing an exact-once replace inside the cell with `python3 -c` assumes a language runtime in the target repo's image. That goes against DESIGN.md:130 ("knows nothing about languages") and CLAUDE.md:94 ("core invokes declared gates, never tools").
  - The body's line (`:92-93`), "None of the byte-level machinery needs to cross into the container", leaves exactly this open.
  - **Fix:** name the mechanism, for example sh and git only, with content passed as argv. Or add `runtime.py` to `touches` with a stated reason.

- **Concern (unverified): `census` may fail the cell.** If replacing the stub deletes `SA-0061`'s `test_the_stub_mutator_makes_the_result_an_honest_skip`, `census` fails on a removed test (`saffron/gates/core/census.py:72-91`). The spec should say whether that test is kept, renamed, or deleted. I could not check this: the test does not exist at base.
