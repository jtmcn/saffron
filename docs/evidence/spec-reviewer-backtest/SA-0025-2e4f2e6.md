I found six blockers, so the spec is not runnable as written. The worst are that criterion 1 would stack a child on a parent that already merged, and that the cell can't check out the parent's commit at all. Everything was read in the working tree, which is the base snapshot. I ran no tests; the claims about runtime behaviour are reasoned from the code.

## Findings

1. **Blocker: criterion 1 stacks a child on a parent that has already merged or been rejected** (spec:74-76 "resolves a dependent's second base from the parent's recorded pushed branch head … leaves it unset when the parent has no pushed branch").
   - **Breaks:** DESIGN.md:379 "A parent whose work is already in the default branch admits its dependent, because a child cut from `base_sha` does have that parent's commits". It also breaks the spec's own criterion 6, "exactly as they do today".
   - **Why the letter goes wrong:**
     - `pushed_sha` is never cleared. `reconcile` only calls `ledger.set_task_state(row["task_id"], new_state)` (reconcile.py:150), and only `set_task_package` writes `pushed_sha` (ledger.py:414). So a `MERGED` or `REJECTED` parent still has a recorded pushed head, and the child gets stacked on the parent's pre-merge commit.
     - The dependency gate never runs on this path. `_run_cell` builds `CellSpec` straight away (cli.py:251-267); `build_queue` is only called from `_queue` (cli.py:328).
     - "The parent's" task is ambiguous: one spec id holds many task rows (ledger.py:243-246).
   - **Fix:** stack only when the parent's newest task at its current `spec_sha` is in `READY_FOR_REVIEW`, `APPROVED` or `MERGE_TRAIN` with a non-empty `pushed_sha`. That is the same row rule `_dependency_refusal` uses (scheduler.py:586-592). A merged or retired parent gets `None`.

2. **Blocker: the cell can't check out the parent sha that criterion 1 resolves.**
   - **Why:**
     - package.py:7-10 says `ensure_mirror` "fetches `+refs/*:refs/*` with `--prune`, so any ref left behind that the local repo does not have is deleted on the next run — including a branch this module just created".
     - `_run_cell` calls `ensure_mirror` on every run (cli.py:219). The parent's branch exists only on the real remote (package.py:697-702).
     - The cell's setup runs `git fetch -q origin && git checkout -q -b {branch} {base_sha}` (worktree.py:89-90). That fetch only brings over commits reachable from `refs/heads/*`, so a sha no branch points to never reaches `/work` and the checkout fails with `CellRuntimeError` (exit 2).
   - **Why no test catches it:** SA-0022's test clones a bare repo whose HEAD *is* the parent (test_worktree.py:684-686), so it never hit this. Criterion 8 (no network, no cell) means no test in this spec will either. The spec itself says a missing piece means "the feature ships broken" (spec:43-44).
   - **Fix:** add a criterion.
     - After `ensure_mirror`, `cli.py` fetches `refs/heads/saffron/<parent>` from the real remote into the mirror, the way `fetch_default_branch` does (package.py:133-141).
     - It then checks the fetched head equals the recorded `pushed_sha`, otherwise `None`.
     - Witness it with a bare local remote, as the `packageable` fixture does (test_package.py:752-775).

3. **Blocker: criterion 3's behaviour is already true at `base`, so its test proves nothing** (spec:80-82; the Problem's claim at spec:60-64 that re-verification "re-appl[ies] the parent's diff a second time").
   - **Evidence:** `patch.diff` is exported against `tree_base` (session.py:524, 533), so it holds only the child's hunks. PACKAGE applies it at `fetch_head` (package.py:554, 567). With the parent merged into `fetch_head`, `base` applies only the child and opens against the default branch. A "parent merges, child re-verifies, parent hunks not re-applied" test therefore passes at `base`.
   - **The real hazard is one this change introduces:** building the child's branch on the parent's branch head (which carries the parent's own commits) and then, after the parent squash-merges, targeting the default branch. Whether this repo squash-merges is **unverified**; mirror.py:54-69 handles both merge shapes.
   - **Fix:** restate criterion 3 as a guard ("once the parent has merged, PACKAGE applies at `fetch_head` and opens against the default branch"). Name its mutant: "apply at the parent's head whenever `tree_base ≠ base_sha`". Correct the Problem sentence.

4. **Blocker: criteria 3 and 4 contradict each other when a merged parent's branch has been deleted.**
   - Criterion 4 (spec:83-85) says "disappeared … is reported as a task failure". Criterion 3 says a parent that merged in the meantime goes on to re-verification.
   - A merged parent's branch is commonly deleted on merge (this repo's setting is **unverified**), so one situation matches both criteria.
   - PACKAGE has no way to know "merged". The ledger says `MERGED` only after `reconcile` runs (reconcile.py:111-112, 150), and `package()` never calls it.
   - **Fix:** say how "merged" is detected (for example `gh pr view saffron/<parent> --json state`, or a `reconcile` pass first), and that merged takes precedence over disappeared.

5. **Blocker: criterion 5 admits children that can't be stacked correctly** (spec:86-89).
   - **Breaks:** DESIGN.md:379 "That is not a smaller version of the feature; it is a version that lies. Without stacking the child branches off `base_sha`, so the parent's changes are not in its tree".
   - **Why:**
     - `CellSpec` has one `stacked_on` (session.py:184). A child with two `READY_FOR_REVIEW` parents is admitted under criterion 5 but can only be stacked on one; the other parent's commits are missing from its tree.
     - The spec's Out of scope says "A grandchild … must not be half-built" (spec:105-107), yet nothing refuses a parent that is itself stacked.
   - **Fix:** admit at most one parent that is neither merged nor retired; refuse the second with a reason naming it. Decide the grandchild case explicitly: refuse it, or add a criterion.

6. **Blocker: no criterion declares a witness or a mutant, and I can name wrong implementations the tests described in the criteria would pass.**
   - The spec has no `acceptance:` block, so `criteria` reports `skip` (DESIGN.md:839) and the PR body will say "not mechanically checked".
   - **Criterion 2:** `base=f"saffron/{spec.depends_on[0]}" if spec.depends_on else default`, which is the route the Notes suggest at spec:119-121. It passes a stacked-child test, but opens an unstacked child of a merged or retired parent against the parent's stale or deleted branch. PACKAGE should decide "stacked" from `patch.json`'s `tree_base != base_sha` (session.py:539-540).
   - **Criterion 4:** checking only `remote_sha(...) == ""` passes a "disappeared" test and ignores "moved".
   - **Criterion 1:** taking the newest row for the parent across every `spec_sha` and state passes a single-row test.
   - **Already fine:** the `preserves` claims have witnesses at `base`. Criterion 6 has `test_this_repos_own_specs_admit_a_merged_parent_and_name_a_retired_one` (test_scheduler.py:873); criterion 7 has test_package.py:1303 and :1536.
   - **Fix:** add an `acceptance:` block with one witness per criterion, `preserves: true` on 6 and 7, and the mutants above.
