## Findings

- **Blocker: claim 2 leaves out "committed", and the witnesses can't detect the gap.** The claim (spec:41-46) says the lenses read the critic cell's tree, "the task's base with the exported patch applied". It doesn't say "committed". Both readers the lenses use look at HEAD, not the working tree:
  - `export_patch` runs `git diff … f"{base_sha}..HEAD"` (`saffron/cell/worktree.py:235`).
  - `read_at_head` runs `git show f"HEAD:{path}"` (`worktree.py:246`).

  So a critic cell that runs `git apply` and never commits gives every lens an empty diff. `anchor` then has no hunks, the review finds nothing, and the task reaches `READY_FOR_REVIEW` without being reviewed. The witness can't see this. The spec says "Test through `_drive`" (spec:154), and `_stub_the_runtime`'s `export_patch` returns the same `patch` whatever container it is called with (`tests/test_session.py:734-736`). A test that only checks which container was used therefore passes. The Context does say "applied and committed" (spec:87-88), but the claim is what the witness proves. **Fix:**
  - Change claim 2 to "applied and committed by that cell's own git".
  - Require its witness to have the stub return a different diff per container.
  - Assert that the lens prompt carries the critic container's diff.
  - Assert that a commit in the critic container comes after the apply and before the first `export_patch(<critic>, …)`.

- **Concern: the golden watch fixture is outside `touches`.** `test_watch_output_matches_the_golden_fixture` (`tests/test_events.py:1667-1695`) compares a green run's watched lines, REVIEW included, exactly against `tests/fixtures/watch-golden.txt:1-19`. Any new line the critic cell prints on the green path (a `preflight:` or `cell:` note, a `teardown:` line) fails `tests`, and neither file can be edited. The spec pushes toward printing one: it says "Bring the critic cell up with the pieces `cell_up` already uses" (spec:124), and `cell_up` prints a line per step (`session.py:862-915`). The rest of test_events.py is safe: it imports `_stub_the_runtime` and `_drive` from test_session (`tests/test_events.py:48-58`), so new stubs reach it. **Fix:** add `tests/fixtures/watch-golden.txt` to `touches`, or say in the Notes that the green path prints nothing new.

- **Concern: a failed apply step isn't always the patch's fault.** CLAUDE.md "Invariants" says "`error` ≠ `fail` … `error` means the gate broke … Never collapse them." The Notes rule out `GATE_ERROR` and runtime failures entirely (spec:148-152). Read literally, every non-zero exit from the apply exec becomes `EXHAUSTED`. But `exec_stream` also returns 124 when it times out (`saffron/cell/runtime.py:563-568`), and a dead container exits non-zero from the runtime itself. Both would be charged to the agent. **Fix:** only git's own refusal to apply means `EXHAUSTED`. A timeout, or a failed exec (probe the container first, or key on git's `error:` stderr), is a `CellRuntimeError`.

- **Concern: no cleanup of critic resources left by a killed run.** `cell_up` removes stale resources before creating anything, and says why: "a leftover network from a SIGKILLed run makes `create_network` the first thing that raises on a re-run" (`session.py:850-854`). The spec's critic cell only has a `finally` (spec:137-138), and a SIGKILL during REVIEW skips it. The next run of this spec then fails when REVIEW creates the critic's volume or container, after IMPLEMENT has already been paid for. **Unverified:** that `create_volume` (`runtime.py:344-346`, `_must`) fails on an existing name. **Fix:** remove the critic's container and both volumes before creating them.

- **Concern: the change is close to the size ceiling, and `size` blocks here.** `risk: elevated` "makes `size` blocking" (`DESIGN.md:1069`), with a `bug` ceiling of 300 (`saffron/gates/core/size.py:25`). My estimate:

  SA-0086, the closest sibling (a fresh cell for item 118), came to 269 lines with three criteria. SA-0070 went EXHAUSTED once at 316. The blocker fix adds a few more test lines.

- **Concern: the isolation claim is only proved against stubs.** CLAUDE.md says "Isolation tests must start a cell the way production does and probe from inside it." Claim 1 is an isolation claim, and its only witness runs against stubs. That's the right choice for a gate, but the operator should file a `cell`-marked follow-up.

- **Note: binary changes won't apply in the critic cell.** `DIFF_FLAGS` has no `--binary` (`worktree.py:131-165`), so a patch with a binary file can't apply there and the task ends `EXHAUSTED`. PACKAGE already refuses such patches as "never appliable" (`saffron/phases/package.py:223-227`), so no shippable task is lost. The failure just moves earlier and is charged to the agent.
