## Findings

- **Blocker: the change is too big for the size gate (check 5).** The gate caps a `feature` at 600 changed lines (`saffron/gates/core/size.py:25`: `_CEILINGS = {"bug": 300, "feature": 600, ...}`). It counts every added or removed line, tests and comments included (`size.py:37-72`). The spec sets `risk: elevated` (spec:25), which makes the cap blocking. Dropping that wouldn't help: `.saffron/policy.yaml:13` lists `saffron/ledger.py` under `elevate_on`, so this change is elevated anyway. My estimate:
  - `intake.py`: joining wrapped criteria plus discovery with a failures list, about 40 lines.
  - `ledger.py`: two read methods, about 30.
  - `scheduler.py`: result types, the two state lists, filter and resume, five refusals, parsing `gh` output, path tokens, ordering. About 200–260.
  - `cli.py`: the subcommand, the export, printing, exit codes. About 50.
  - `test_intake.py`: about 50.
  - `test_scheduler.py`: five refusals, the five re-queue states, the done states, the resumed `task_id`, the glob, bare-filename and empty-`touches` cases, a fake `gh`, ledger setup. About 250–320.
  - `test_cli.py`: about 70–90. Every CLI test repeats about 8 lines of monkeypatch setup (`tests/test_cli.py:78-85`).
  - That totals about **690–840 lines**. Written unusually tersely it's about 560. This repo's comment density makes the high end likelier.
  - **Fix:** split the spec. For example: first spec is the criterion join, discovery and the offline refusals; second is the two GitHub-backed refusals.

- **Blocker: the path-token rule would refuse this repo's own runnable specs (checks 1 and 6).** Criterion 8 (spec:66) says a criterion "names a path" when it contains "a repo-relative path token". It adds that "a bare filename is **not** matched against a `touches` entry that differs by directory".
  - Read literally, SA-0001 gets refused. Its criterion "No file under `saffron/` is changed" (`SA-0001-factory-ontology.md:91`) names `saffron/`, which doesn't match its `touches` (`ontology/**`, `tests/ontology/**`). That criterion forbids a path; it doesn't need one.
  - If bare filenames count as tokens, more get refused:
    - SA-0008, for "`rebut.py` exposes…" (`SA-0008…md:63`) and "`package.py` supplies…" (`:74`).
    - SA-0001 again, for `plan.json` and `scope.json`.
    - Possibly SA-0009 itself, for `scope.matches`.
  - This contradicts the spec's own smoke check (spec:123-126: "`SA-0001` and `SA-0008` queued … **and nothing refused**"). It is also the failure DESIGN warns about (`DESIGN.md:376`): "a false refusal at gate 0 costs a whole spec overnight".
  - **Fix:** define the token precisely. For example: a backticked token containing `/` and not ending in `/`. Say whether a bare filename is ignored or refused, and whether a token matching `forbidden` is exempt. Add a test that SA-0001's negative criterion is not refused.

- **Blocker: the spec's claim about SA-0005 is false (check 6).** Spec:53-55 says `saffron/cli.py` and `saffron/phases/package.py` "sit on continuation lines" of SA-0005's criteria. Neither string appears anywhere in `.saffron/specs/SA-0005-size-wiring.md`; I grepped it at base with no match.
  - Its criteria (lines 51-67) reach those files only by meaning ("the PR body header and the queue line"). `DESIGN.md:372` and `docs/BACKLOG.md:1127-1130` describe it the same way.
  - Criterion 1 (spec:59) is built on "the `SA-0005` shape" yielding "the path token from its continuation line".
  - After the parse fix, the real SA-0005 would still pass this refusal. A cell that writes the test the notes invite ("both measured on the real spec", spec:113-114) would fail. It can't edit that spec either, because `.saffron/**` is forbidden. The rule also can't catch the case the spec gives as its motivation.
  - **Fix:** write out the multi-line fixture literally, and state that the real SA-0005 is not refused by this rule.

- **Blocker: the "no `ORPHANED` stamp" check in criterion 11 can't fail (check 3).** Criterion 11 (spec:69) tests against "a ledger the repo has never been seen in". That ledger has no tasks for the repo, so no in-flight task exists to stamp. An implementation that does stamp `IMPLEMENTING` tasks as `ORPHANED`, which spec:95-97 forbids, would still pass.
  - **Fix:** add a second fixture with a task left in `IMPLEMENTING` for this repo, and assert its state is unchanged.

- **Blocker: criterion 6's test can't tell the right filter from the one DESIGN rejects (check 3).** DESIGN says to queue a spec unless it has a task in a "done" state, and rejects the positive form ("queue if a re-queueing task exists") (`DESIGN.md:364`: "The positive form … is the one to reject").
  - A test that gives each re-queue state on its own a single task passes both forms.
  - Where they differ: a spec with a `RATE_LIMITED` task and a `READY_FOR_REVIEW` task at the same sha. The positive form queues it; the correct filter does not.
  - **Fix:** name that case as a required test. Also say which `task_id` resumes when several re-queueing tasks share one sha.

- **Blocker: criterion 7's open-PR refusal can be keyed on the spec instead of the task (check 3).** DESIGN keys this refusal on the task (`DESIGN.md:340`: "Refusal is keyed on `task_id`, not on the spec").
  - A refusal that fires on any open PR from branch `saffron/<id>` (`cli.py:170`) passes a test that uses a spec with no task.
  - It would then wrongly refuse a `CHANGES_REQUESTED` task on its own PR.
  - Telling "another task" apart also needs `tasks.pr_url`, but criterion 4 (spec:62) only asks the ledger query for "state".
  - **Fix:** require the own-PR test (the resumed task's own PR is not refused), and add `pr_url` to criterion 4.

- **Needs your call: the spec declares no mutants (check 3).** It edits existing code but has no `mutant`, `witness` or `preserves` entries. `docs/agents/issue-tracker.md` at base doesn't define those fields, and no spec in `.saffron/specs/` uses them.
  - Example of what one would catch: criterion 1's test passes a join that pulls later section text into the last criterion. `_CRITERIA_SECTION` stops only at `^##\s` (`intake.py:23`), so SA-0001's "### The five queries" table (`SA-0001…md:94`) sits inside its criteria section. A naive join appends it to the last criterion, which then lands in the PR body (`pr_body.py:128`).
  - **Fix:** add a test that SA-0001's last criterion ends at its own text.

- **Concern: `gh` failure is unspecified.** Criterion 9 (spec:67) says how `gh` is injected, not what happens when it fails. Reading a failed `gh pr list` as "no open PRs" would silently queue everything. That breaks the spirit of the `error` ≠ `fail` invariant in CLAUDE.md ("Never collapse them"). **Fix:** state that a `gh` that could not run exits `2`.

- **Concern: the same repo may have several ledger rows (unverified).** Criterion 4 resolves a repo to one id. But a repo's origin is stored in more than one form:
  - `session.py:546-548` falls back to `origin_url = str(repo)`.
  - `replay.py:53` stores `str(repo_dir)`.
  - `DESIGN.md:305` says v0 and v0.5 "stored the mirror's source in both" fields.

  Tasks recorded under a local-path origin would be invisible, and their specs would re-queue. I couldn't check your `~/.saffron/ledger.db`, so the smoke check is unverified.

- **Concern: nowhere to report in-flight tasks.** Spec:95 says in-flight states are "reported, not repaired". Criterion 5 (spec:63) only has a queue and refusals, and `DESIGN.md:366` says not to treat an in-flight state as "queue it". **Fix:** name where such a spec appears in the output.

- **Concern: "writes nothing at all" is ambiguous.** `cli.py:74` opens the ledger before choosing a subcommand. Opening it runs the schema, `ALTER TABLE` (`ledger.py:136`), a backfill `INSERT` (`ledger.py:148-156`) and possibly a table rebuild (`:173-202`). On an older ledger, `saffron queue` writes. **Fix:** say whether migrations count, or require a read-only open for `queue`.
